# AI Council v0.1 设计规格

日期：2026-08-31
状态：已批准，等待实现计划

## 1. 产品定义

AI Council 是一个面向软件开发任务的多模型决策与执行系统。用户向系统描述开发需求，多个不同厂商的模型先独立提出方案，再匿名交叉评审，由独立 Judge 形成最终执行计划。系统只有在用户明确批准不可变的执行快照后，才允许修改本地项目或运行命令。执行结果必须经过确定性工具验证，失败证据会返回理事会重新规划。

产品的核心价值不是增加模型对话数量，而是提供可审计的决策过程和有验证的执行闭环。

## 2. v0.1 目标

- 通过 Web 控制台操作 AI Council。
- 接入用户自带密钥的 OpenAI、Anthropic 和 DeepSeek API。
- 只操作用户通过本地 Workspace Runner 明确授权的项目目录。
- 支持独立提案、匿名互评、Judge 裁决和 Devil's Advocate 审查。
- 在执行前展示完整文件 Diff、命令、风险、费用和测试计划，并等待用户批准。
- 仅执行与批准快照完全一致的补丁和命令。
- 对 Go 和 Node.js/TypeScript 项目执行基础构建、静态检查和测试。
- 保存任务状态、结构化产物、模型用量和不可变审计事件。
- 支持浏览器断开后恢复任务视图，以及验证失败后一次重新规划。

## 3. 非目标

v0.1 不包含远程 GitHub/GitLab 仓库、多用户和 RBAC、云端执行节点、本地模型、任意工具市场、移动端、完全自主执行和生产级分布式部署。系统会为这些能力保留清晰接口，但不会在首版提前实现。

## 4. 技术约束与总体架构

技术栈固定为：

- Go 1.25
- go-zero
- Gin
- GORM
- gRPC
- React
- Next.js App Router

首版采用两个后端进程，避免过早拆分成大量微服务：

```text
Next.js + React Web Console
          │ REST / SSE
          ▼
go-zero Council Server
          ├── API 与事件流
          ├── 原生混合状态机
          ├── 模型 Provider 与 Council 协议
          ├── 审批、预算和审计
          └── GORM 持久化
                    │ gRPC
                    ▼
Gin Workspace Runner
          ├── 本地连接授权与健康接口
          ├── 项目目录和路径边界
          ├── Git、补丁和文件快照
          ├── 受限命令执行
          └── 验证与日志回传
```

### 4.1 Web Console

Next.js 负责页面路由和服务端页面外壳，React 负责交互式任务工作台。浏览器通过 REST 创建和操作任务，通过 SSE 接收带递增序号的任务事件。断线重连时，客户端携带最后事件序号继续读取。

### 4.2 Council Server

go-zero 提供对外 REST API、SSE 事件流、任务生命周期、超时重试和服务配置。状态机使用 Go 原生代码实现，状态和合法迁移由显式定义控制，不依赖模型判断。GORM 负责关系数据和事务。

### 4.3 Workspace Runner

Runner 是唯一可以访问项目文件和启动子进程的组件。Gin 只承载本地授权、健康检查和诊断接口；Council Server 与 Runner 的执行协议使用 gRPC。Runner 默认只监听回环地址，注册时创建短期配对凭据。

### 4.4 模型 Provider

所有厂商实现统一的 `ModelProvider` 能力接口，输入和输出使用版本化结构。OpenAI 与 Anthropic 使用各自官方 Go SDK；DeepSeek 使用独立 HTTP Provider。Provider 负责超时、限流、重试、错误规范化、流式结果和用量统计，不负责决定 Council 流程。

## 5. 混合状态机

安全和治理阶段固定，参与模型、动态角色、评审分配和有限讨论轮次可以根据任务调整。

```text
DRAFT
  -> ANALYZING
  -> PROPOSING
  -> REVIEWING
  -> JUDGING
  -> RED_TEAM
  -> AWAITING_APPROVAL
  -> EXECUTING
  -> VERIFYING
  -> SUCCEEDED

VERIFYING --失败且未达到重规划上限--> REPLANNING -> REVIEWING
任一可恢复阶段 --用户取消--> CANCELLED
任一不可恢复错误 --记录证据--> FAILED
```

只有状态机代码能够迁移状态。模型只能生成相应阶段允许的 Artifact。非法迁移、过期版本和不满足法定人数的结果会被拒绝。

## 6. Council 协议

### 6.1 结构化产物

- `TaskBrief`：需求、项目事实、约束、验收标准和允许目录。
- `Proposal`：方案、技术理由、涉及文件、风险、测试策略和证据引用。
- `PeerReview`：对匿名方案的正确性、可行性、风险和遗漏检查。
- `CouncilDecision`：Judge 的比较、采纳与拒绝理由、最终混合方案。
- `RedTeamReport`：对最终方案的反例、攻击面和失败条件。
- `ExecutionPlan`：精确文件补丁、命令参数、预期结果和恢复方式。
- `ApprovalSnapshot`：用户批准的计划版本、内容哈希和决定。
- `VerificationReport`：实际 Diff、测试、静态检查、验收项和审查结果。

所有 Artifact 带 `schema_version`、唯一 ID、父版本、创建阶段和内容摘要哈希。

### 6.2 协商规则

1. 默认三席提案模型并行工作，首轮互相不可见。
2. 角色根据任务动态分配，不把厂商永久绑定为固定角色。
3. 互评阶段将厂商和模型名称替换为 `Proposal A/B/C`。
4. 模型不能评审自己的方案，分配关系由服务端确定。
5. Judge 不参加首轮提案，并按正确性、需求匹配、实施成本、风险、可维护性和可验证性裁决。
6. Devil's Advocate 在审批前尝试推翻胜出方案；发现实质问题时退回 Judge。
7. 模型自报分数不是事实置信度，只用于调度。代码质量以构建、测试、静态检查和验收证据为准。
8. 每次运行有最大轮次、Token、费用和时间预算。
9. 可用模型少于配置的法定人数时暂停任务，不将单模型结果标记为委员会共识。

## 7. 审批协议

进入 `AWAITING_APPROVAL` 前，系统必须生成完整的 `ExecutionPlan`，包括：

- 新增、修改和删除的文件清单。
- 可审阅的统一 Diff。
- 每条命令的可执行文件、参数、工作目录、超时和用途。
- 风险等级、预计模型费用和预计执行时间。
- 格式化、构建、静态检查、测试和验收步骤。
- 失败后的恢复方式。

用户批准后生成不可变的 `ApprovalSnapshot`。快照哈希覆盖计划版本、补丁、命令、路径范围和验证步骤。Runner 必须重新计算并校验哈希。任何新增命令、补丁改变、路径扩大或计划换版都会使批准失效并退回审批状态。

只读分析不需要逐次批准，但必须受项目路径和敏感文件策略限制。文件写入、命令执行和外部副作用始终需要批准。

## 8. 执行安全

- 每个 Workspace 保存用户授权的规范化根路径。
- Runner 对目标路径执行绝对化和真实路径解析，拒绝 `..`、符号链接或目录联接逃逸。
- 默认拒绝读取 `.env`、凭据文件、私钥、常见密钥目录、数据库文件和大型二进制文件。
- API Key 不得进入 Artifact、模型上下文、项目文件、数据库或日志。
- 命令使用可执行文件加参数数组启动，不将模型字符串直接交给 Shell。
- 每条命令带独立超时、输出上限和取消上下文。
- v0.1 不向执行命令提供任意外网访问能力；模型 Provider 的网络访问与 Runner 隔离。
- Runner 只接受已配对 Council Server 的 gRPC 请求，并验证请求版本、任务 ID、批准快照和幂等键。
- 重复请求必须返回原执行结果，不得重复应用补丁或命令。

## 9. 文件保护与恢复

执行前记录项目 Git 状态和所有目标文件快照。系统不得使用 `git reset --hard`、`git checkout --` 或其他可能覆盖用户工作的恢复方式。

任务的变更集必须与执行前用户已有变更区分。系统只允许改动批准计划中的文件和范围，并在执行后比较实际 Diff。失败时保留现场，向用户提供重新规划、保留本次修改或恢复本次修改的选择。恢复只处理本次任务记录的变更，并写入审计事件。

对于非 Git 项目，同样使用目标文件快照和内容哈希实现范围检查与恢复。

## 10. 验证流程

验证优先使用确定性工具：

1. 校验实际 Diff 未超出批准范围。
2. 运行批准的格式化命令。
3. 运行构建和静态检查。
4. 运行相关测试和用户指定的验收命令。
5. 检查每条验收标准是否有对应证据。
6. 由未参与执行的 Review Agent 进行补充逻辑和安全审查。

确定性检查失败时，AI 审查不能将任务标记为成功。v0.1 允许最多一次携带失败证据的重新规划，新的补丁和命令必须重新审批。

## 11. Web 控制台

### 11.1 页面

- 模型配置：录入会话密钥、测试连接、选择模型和预算。
- 项目管理：与 Runner 配对、选择本地目录、查看技术栈和 Git 状态。
- 创建任务：输入需求、验收标准、约束、预算和委员会配置。
- 任务工作台：查看阶段时间线、提案、匿名互评、裁决、费用和错误。
- 审批与结果：审阅 Diff 和命令、批准或拒绝、查看执行日志和验证报告。

### 11.2 工作台布局

左侧显示任务阶段、项目上下文和 Council 时间线；中间显示当前 Proposal、Review、Diff、执行或验证内容；右侧显示模型角色、用量、费用、错误和重试信息。

危险操作使用清晰的独立确认区，不将批准按钮与普通导航操作混在一起。

## 12. 数据模型

- `Workspace`：本地根路径、Runner、授权状态和安全策略。
- `ProviderProfile`：厂商、模型和非密钥参数。
- `Task`：需求、约束、验收标准和当前状态。
- `CouncilRun`：运行预算、法定人数、阶段和重规划次数。
- `Seat`：本轮 Provider、模型、动态角色和权限。
- `Artifact`：类型、版本、摘要、哈希和文件位置。
- `ModelInvocation`：请求阶段、耗时、Token、费用和脱敏错误。
- `Approval`：快照哈希、计划版本、决定、时间和操作者。
- `ExecutionStep`：补丁或命令、幂等键、状态和实际结果。
- `AuditEvent`：只追加的状态变化、安全事件和关联对象。

SQLite 保存关系数据；完整大体积 Artifact 以 JSON 文件写入应用数据目录，数据库保存索引和校验值。GORM 模型预留 `owner_id`，但 v0.1 按单用户运行。

## 13. 错误处理与恢复

- Provider 超时或限流：在预算内指数退避；超过阈值后标记席位不可用。
- 法定人数不足：暂停并要求用户调整席位或重新提供 Provider。
- 结构化输出无效：同一模型进行一次受约束修复；仍无效则记录失败。
- Council Server 重启：从数据库状态和最后事件恢复，不重复已完成调用。
- SSE 断开：客户端按事件序号续传。
- Runner 失联：保持待执行或执行状态，禁止换 Runner 后盲目重放；恢复后通过幂等键查询结果。
- 补丁冲突：不强行覆盖，退回重新规划。
- 命令失败或超时：保存 stdout、stderr、退出码和超时证据，进入验证失败流程。
- 审批过期或哈希不符：拒绝执行并生成安全审计事件。

## 14. 测试策略

- 状态机单元测试：覆盖所有合法迁移和非法迁移。
- Council 协议测试：覆盖匿名化、自评阻止、法定人数和预算停止条件。
- Provider 合约测试：使用伪服务器验证三个 Provider 的规范化行为，不依赖真实密钥。
- 审批安全测试：覆盖补丁、命令、路径和计划版本篡改。
- Runner 路径测试：覆盖路径穿越、符号链接、目录联接和非授权目录。
- 幂等性测试：重复执行请求不能重复产生副作用。
- 文件保护测试：验证脏工作树和非 Git 项目不会丢失原内容。
- gRPC 集成测试：验证配对、执行、日志和错误协议。
- Web 测试：覆盖模型配置、任务创建、SSE 恢复、审批和报告页面。
- 端到端验收：在示例 Go 项目和 Next.js 项目中完成一次批准后的代码修改及验证。

## 15. v0.1 验收标准

1. 用户可以配置并测试 OpenAI、Anthropic 和 DeepSeek 的会话密钥。
2. 用户可以授权一个本地项目目录并创建软件开发任务。
3. 三席模型能够生成互相隔离的独立提案。
4. 匿名互评不泄露模型身份，且不允许自评。
5. 系统可以生成包含 Diff、命令、风险和测试方案的最终计划。
6. 未批准时，系统不能修改文件或执行命令。
7. Runner 会拒绝任何与批准快照不一致的请求。
8. 批准后可以完成真实代码修改并返回构建、测试和审查结果。
9. 浏览器断开重连后可以恢复任务状态和事件。
10. API Key 不进入数据库、日志、项目文件或模型上下文。
11. 执行失败不会覆盖用户执行前已有的修改。
12. 状态机、权限边界、路径安全、审批哈希和幂等执行均有自动化测试。

## 16. 扩展方向

按以下顺序扩展：动态席位和领域专家、搜索与 MCP 工具、本地模型、GitHub/GitLab、团队权限、分布式 Runner、A2A 智能体互操作。

Provider、Verifier、Tool 和 Runner 均通过版本化接口扩展。扩展模块不能绕过固定状态机、审批门和审计链。
